# Research: skills and tools for driving Blender and building the 3D page

Searched on GitHub and the web in late November 2026; every repository in the verified list was then checked independently by reading its README, LICENSE, skill files and source in a shallow clone, including what it executes on the machine and where it connects. blender.org and projects.blender.org were not reachable from the research machine, so statements about the official Blender Lab bridge are second-hand.

## Bottom line

- No single skill does the whole job (a human figure, a sewn and draped heavy-cotton T-shirt with front and back prints, baked textures, a phone-ready GLB, and a three.js page around it). It has to be assembled, and the garment and figure steps are best kept as this project's own scripts.
- The lowest-exposure way to let an assistant use Blender is without a live bridge: it writes Blender Python and runs Blender in the background (`blender -b --factory-startup -P script.py`). A live bridge only adds watching and inspecting the open Blender window. Every bridge runs arbitrary Python as the logged-in user.

## Proposed set for the PC

| purpose | tool | why | cautions |
|---|---|---|---|
| Blender know-how and helper scripts | `EL4CTEO/blender-skills` (MIT) | 28 skills with bundled, tested Blender scripts (clothing, baking, retopology, checks, web GLB export preset); no network code, no telemetry | needs Blender 5.2 LTS or newer; aimed at game assets; one of its rule files tells the agent to run scripts without reading them: read them anyway; pin a version |
| Watching Blender live (optional) | the official Blender Lab bridge (`lab/blender_mcp` on projects.blender.org, extension from lab.blender.org) | official, minimal: scene summaries, screenshots, run code | Blender 5.1 or newer; no guards and no authentication by design; not verified at source here; install only from the official address |
| Human figure | `makehumancommunity/mpfb2` (add-on GPL, assets and output CC0) | scriptable human generator with rigs; no GPU, no network code | install only from the official extensions platform or the project's own organisation; asset packs have a licence per pack (some need credit) |
| glTF export and optimisation | Blender's bundled exporter (`KhronosGroup/glTF-Blender-IO`), `donmccurdy/glTF-Transform` (MIT), optionally `zeux/meshoptimizer` gltfpack (MIT) | mature, scriptable, no network code | keep named meshes: avoid options that join or prune nodes |
| three.js know-how | `CloudAI-X/threejs-skills` (MIT) | 13 reference skills, text only | its examples load three.js from a public CDN: this project bundles it locally instead |
| Testing in a real browser with the real GPU | `microsoft/playwright-mcp` (Apache-2.0) | screenshots, console, network, phone emulation | pin the version and start it with `--isolated --no-webmcp`; it is not a security boundary |
| Page checks and budgets (ideas and scripts) | `Moh4696/open-3d-skills` (site-check), `yogeshkumbhat/3d-web-revamp` | useful check scripts and fallback rules | young, single-author projects: copy only the parts used, pin, read before running |

Usable but with a weaker safety record: `ahujasid/mcp-for-blender` (the most used community bridge). Telemetry is on by default, its socket is unauthenticated and it had several security advisories in 2026. If it is used at all: turn telemetry off, enable its safe mode, one bridge at a time.

Do not install: `DmitriyGolub/threejs-devtools-mcp` (opens a proxy on the local network that anyone on the same Wi-Fi can reach), and any of the look-alike repositories named like `blender-ai-copilot-*` or unofficial MakeHuman builds that the search surfaced: they fit a known malware distribution pattern. Keep Blender's "Auto Run Python Scripts" off and do not open .blend files from unknown sources.

## Verified repositories

### microsoft/playwright-mcp

- Verdict: **recommend**; kind: mcp-server (npm @playwright/mcp); the repo is a thin package, the server source lives in microsoft/playwright packages/playwright-core/src/tools; commercial use: yes; stars 40163; last push 2026-11-18
- Licence: Apache License 2.0 (LICENSE read; package.json "license": "Apache-2.0")
- Install: README, Claude Code section, verbatim: `claude mcp add playwright npx @playwright/mcp@latest`. Requirements line: 'Node.js 20 or newer'. For this project pin and harden it: `claude mcp add playwright -- npx @playwright/mcp@0.0.86 --isolated --no-webmcp`, and add `--caps vision` if Claude must drag on the canvas. Alternative the README itself suggests for coding agents (microsoft/playwright-cli README): `npm install -g @playwright/cli@latest` then `playwright-cli install --skills`, which installs into .claude/skills.
- What it can do: Claude can open the locally served page, take screenshots (browser_take_screenshot), read console messages and network requests (failed GLB or decoder loads), run JS in the page (browser_evaluate, for example to read renderer.info), resize the window and emulate a phone (--device "iPhone 15", --mobile, --viewport-size). Limits for a 3D page: the server works from accessibility snapshots by default and a WebGL canvas is opaque there, so screenshots are needed; coordinate mouse tools are opt-in (--caps vision). file: URLs are blocked by default (backend/context.ts), so the page must be served over http://localhost. It does not understand the 3D scene and does not measure phone performance.
- Requirements: Node.js 20 or newer (package.json engines). Default browser is the installed Google Chrome (config.ts sets channel 'chrome'), headed, so WebGL uses the PC's real GPU; other browsers are downloaded by Playwright. Windows, macOS, Linux. No account or key.
- What runs on the machine: A Node process started by npx with the user's privileges, which launches a real browser using a dedicated persistent profile under the ms-playwright cache directory (not the user's own Chrome profile; --isolated keeps it in memory). Two code-execution tools are in the always-on core set: browser_evaluate (JS in the page) and browser_run_code_unsafe, which runs a model-supplied JS function in the server's Node process via vm.runInContext with fetch and Buffer exposed; the README labels it 'RCE-equivalent'. Neither has a confirmation step in the server; Claude Code's permission prompt is the only gate. File output is restricted to the workspace root unless --allow-unrestricted-file-access is passed.
- Network and telemetry: No telemetry or analytics code found by grep in packages/playwright-core/src/tools. Outbound: the npm registry (npx); browser downloads from cdn.playwright.dev and playwright.download.prss.microsoft.com, and edgeupdates.microsoft.com for Edge (server/registry/index.ts), only when a Playwright-managed browser is installed; then whatever sites the browser is told to open, plus the browser's own background traffic. No API keys.
- Security notes: README: 'Playwright MCP is **not** a security boundary', and --allowed-origins / --blocked-origins are stated not to be security boundaries. CVE-2025-9611 (DNS rebinding against the HTTP transport, versions before 0.0.40) is fixed; current is 0.0.86 and the default stdio setup does not open a port. WebMCP is enabled by default: a page can register tools that are surfaced to the model (marked untrusted); disable with --no-webmcp. Any page content is a prompt-injection channel, so keep it on localhost and never use --extension, which attaches to the user's logged-in browser. `@latest` is unpinned and the package depends on alpha builds of Playwright (1.66.0-alpha-2026-11-18). AGENTS.md and .claude/skills/release.md in the repo are instructions for the maintainers' own agents (release process); not addressed to users and not followed.
- Maturity: Very active, Microsoft-maintained, pre-1.0 versioning (0.0.86) with frequent releases; HEAD commit 2026-11-18.
- Corrections found during verification: Stars 40,163 and push date confirmed; playwright-cli confirmed at 15,486 stars, Apache-2.0, pushed 2026-11-24. Omitted by the searcher: browser_run_code_unsafe is a core tool that executes model code in the Node process. 'Safest' is the searcher's wording, not the README's. Defaults differ between the two routes: the MCP server is headed and uses installed Chrome; the CLI is 'headless by default'. Telemetry: none found in source (the searcher only said it was not mentioned). The file: block means the page must be served over HTTP. The claim that headless WebGL is software-rendered is not addressed in the repo; running headed, which is the MCP default, avoids the question.

Relevant here: export_asset.py `--preset web` writes GLB with WebP (q85) and meshopt, `--draco` switches to Draco, KTX2 only on Blender 5.3 via `--set` flags, and it parses the GLB and returns mesh, material, image and triangle counts, extensions and file size; bake_maps.py bakes normal/AO/curvature/ID high-to-low or self-bakes base colour/roughness/metallic in Cycles, packs ORM, picks a GPU and falls back to CPU; sim_setup.py sets up classic cloth (cotton, denim, leather, rubber, silk presets, pin group, colliders) or the 5.2 node-based cloth and bakes by stepping frames; qa_check.py, review_shots.py (contact sheets), mesh_stats.py (`web` budget: 30k tris per character, 2 materials, 2k textures), auto_retopo.py, uv_pack.py, rigify_build.py, bind_mesh.py, stress_poses.py, turntable.py. ### donmccurdy/glTF-Transform

- Verdict: **recommend**; kind: library and CLI (npm @gltf-transform/core, extensions, functions, cli); commercial use: yes; stars 2104; last push 2026-10-20
- Licence: MIT (LICENSE.md read: 'The MIT License (MIT) Copyright (c) 2024 Don McCurdy')
- Install: README verbatim: `npm install --global @gltf-transform/cli`, then `gltf-transform --help` and `gltf-transform optimize input.glb output.glb --texture-compress webp`. Scripting: `npm install --save @gltf-transform/core @gltf-transform/extensions @gltf-transform/functions`. For a repeatable build, install it as a pinned devDependency in the site repo instead of globally.
- What it can do: 39 CLI commands (packages/cli/src/cli.ts), including inspect, validate, optimize, dedup, prune, weld, simplify, join, flatten, draco, meshopt, quantize, resize, webp, avif, png, jpeg, etc1s, uastc, tangents, unwrap and palette. Claude runs it on the GLB that Blender exports and uses `inspect` to report triangle counts and texture sizes against a phone budget. Important for a skinned, printed garment: `optimize` defaults are simplify=true, palette=true, flatten=true, join=true, compress=meshopt, texture-size=2048, texture-compress=auto. Start with `--simplify false --palette false` and choose `--compress` and `--texture-compress` to match the decoders the three.js page loads. join() skips skinned nodes and flatten() preserves joints (functions/src/join.ts, flatten.ts).
- Requirements: Node.js 20 or newer (packages/cli/package.json engines). sharp ~0.35.3 as a native dependency with prebuilt binaries. KTX2 commands (etc1s, uastc, --texture-compress ktx2) need the separate KTX-Software 4.4.0 or newer `ktx` binary on PATH (transforms/toktx.ts). No GPU, no account.
- What runs on the machine: A Node CLI with the user's privileges, working on local files. It spawns the external `ktx` program only for KTX commands. The experimental `--config <path>` option imports a JS module, so it runs code only if a config file is supplied. It executes no model-written code unless Claude writes a build script with the SDK, which is ordinary reviewable project code.
- Network and telemetry: None found: grep of packages/cli/src, cli/bin and packages/functions/src shows no fetch, http, telemetry or analytics; the only process use is spawning `ktx`. Reading models from URLs is off unless `--allow-net` is passed. Install-time traffic is the npm registry only. No keys.
- Security notes: No advisory naming @gltf-transform was found. Its dependency sharp has 2026 advisories reported by search (fixes in 0.35.0, 0.35.4 and 0.35.5; not opened at source); the CLI requires sharp ~0.35.3, so a fresh install should resolve to the latest 0.35.x. Confirm with `npm ls sharp` that it is 0.35.5 or newer. Exposure is low because it only processes the project's own files. Nothing suspicious in the files read.
- Maturity: Mature and maintained: v4.5.1 (lerna.json), v4.6 in progress in CHANGELOG, HEAD commit 2026-10-16. Single maintainer.
- Corrections found during verification: Canonical name is donmccurdy/glTF-Transform. Version is 4.5.1. simplify and weld do exist as CLI commands (cli.ts lines 995 and 1117). The KTX-Software dependency is confirmed in source with a minimum of 4.4.0, not just remembered. Node requirement is 20 or newer. AVIF is also supported. Not mentioned by the searcher: `optimize` simplifies, joins, flattens and palettes by default, which is risky for a skinned figure with print UVs unless switched off.

### KhronosGroup/glTF-Blender-IO

- Verdict: **recommend**; kind: Blender add-on (`io_scene_gltf2`, the official glTF 2.0 importer/exporter bundled with Blender); not a Claude skill, it is the operator a skill or script calls; commercial use: yes; stars 1688; last push 2026-11-26
- Licence: Apache-2.0 (LICENSE.txt read; source headers say 'Copyright 2018-2021 The glTF-Blender-IO authors', bl_info author 'Blender Foundation, Khronos Group'). The licence covers the add-on code, not the GLB files it writes.
- Install: Nothing to install: README says the add-on is bundled and enabled by default in Blender 2.80 and later. The README's only install text is for testing development versions: copy `addons/io_scene_gltf2` into the `scripts/addons_core/` directory of the Blender installation and enable it under Add-ons. The owner should not do that; use the copy that ships with their Blender release.
- What it can do: From addons/io_scene_gltf2/__init__.py: operators `bpy.ops.export_scene.gltf` (bl_idname at line 1967) and `bpy.ops.import_scene.gltf`. Export options relevant here, read in source: `export_format` (GLB or separate), `use_selection`/`use_visible`/collection filters, `export_apply` (default False; its own description warns that applying modifiers prevents exporting shape keys), `export_skins` (default True), `export_influence_nb` (default 4 bone influences), `export_morph` (shape keys as morph targets, default True), animation options (NLA merge modes, sampling, bake), `export_image_format` (AUTO, JPEG, WEBP, NONE), Draco (`export_draco_mesh_compression_enable` plus quantisation levels), `export_materials`, `export_tangents`, `export_extras`, GPU instancing, lights, KHR_materials_variants. Version differences I verified by reading each release branch: Blender 4.5 LTS (add-on 4.5.47) has `export_image_add_webp`, Draco and optional gltfpack, no meshopt, no KTX2; Blender 5.2 (5.2.39) adds `export_meshopt_compression_enable`, still `export_image_add_webp`; Blender 5.3 (5.3.43) renames that to `export_image_add_compressed_images` with `export_compressed_images_type` WEBP or KTX2, `export_compressed_images_fallback` and `export_use_ktx_compression` (Zstandard). A script written for one version fails on another with an unknown-keyword error, so Claude must check the Blender version or the operator's properties first.
- Requirements: Any Blender from 2.80; the main branch now declares add-on version 5.4.20 with minimum Blender 5.3.0, and each Blender release has its own branch (blender-v4.5-release through blender-v5.3-release exist). Works on Windows, macOS and Linux as part of Blender; no GPU needed. Draco and meshopt use native libraries that ship inside Blender.
- What runs on the machine: Python inside Blender's own process, with the user's privileges, only when an import or export is invoked. It loads Blender's bundled native Draco and meshopt libraries through ctypes (blender/imp/draco_compression_extension.py, io/exp/meshopt.py) and, only if the user enables gltfpack and sets a binary path in the add-on preferences, runs that external binary with subprocess (blender/exp/export.py line 503). Other add-ons can hook into export through the user-extension mechanism. It executes no model-written code by itself; Claude's script merely calls the operator.
- Network and telemetry: None. Grep over the whole add-on for urllib, requests, http.client, socket, urlopen, webbrowser, telemetry and analytics returned only shader-node 'socket' identifiers. The only URLs are the documentation and issue-tracker links in bl_info. No accounts, no keys.
- Security notes: Nothing found in the source. A web search for advisories on Blender's glTF add-on returned none (results were about Assimp and tinygltf, different code). General caution only: importing a glTF file from an unknown source means parsing third-party data, and enabling gltfpack makes the add-on run whatever binary path is configured.
- Maturity: Official and continuously maintained: Khronos repository mirrored into Blender's own source tree, CI with glTF-validator round-trip tests, pushed on the day of this check, per-release branches. The README's version table is stale (it still calls 5.0 the current stable and says main will become 5.2), so rely on the branches and bl_info, not on the README.
- Corrections found during verification: Confirmed: bundled and enabled by default, Apache-2.0, stars, push date, operator name `export_scene.gltf` (the searcher had it from memory), and the Blender 5.3 options `export_image_add_compressed_images` and `export_compressed_images_type` WEBP|KTX2 (present in blender-v5.3-release and main). Corrections: (1) 'main branch tracks Blender 5.2+' comes from the outdated README; bl_info on main is version (5, 4, 20), blender (5, 3, 0). (2) Draco options do exist in every branch checked; KTX2 exists only from 5.3; meshopt exists from 5.2 and not in 4.5 LTS. (3) The option was called `export_image_add_webp` up to 5.2, so the 5.3 names break on older Blender and the old name breaks on 5.3. (4) Important for cloth: `export_apply` is False by default and turning it on drops shape keys, so a simulated or sculpted drape must be applied to the mesh deliberately before export, and a skinned garment exports at most 4 bone influences per vertex by default. (5) Canonical casing is KhronosGroup/glTF-Blender-IO. The caveats about triangulation, vertex splitting at seams and baking procedural shaders are properties of glTF itself and are consistent with what I read, but I did not find them stated in this repo's README.

At start-up, not on first tool use, it opens an HTTP reverse proxy and WebSocket server on port 9222 and opens the default browser with child_process.exec (`start`, `open` or `xdg-open`), or launches Chrome through puppeteer-core when PUPPETEER, HEADLESS or CDP_PORT is set. It injects its bridge script into every HTML response it proxies. run_js runs model-written JavaScript in the page with `new Function`, inside the browser sandbox rather than Node, gated only by the client's tool permission prompt. It writes files only under <working directory>/screenshots and reads the working directory's package.json and any path passed to gltf_to_r3f.
- Network and telemetry: No telemetry or analytics found in src. Outbound: probes of localhost ports 3000, 5173, 8080, 4200, 8000, 1234, 4321, 3001, 5174 and 8081 to find a dev server; proxied requests to the dev target, or to a remote host if DEV_URL or set_dev_url is used; the npm registry on each npx start. Listening is the problem: src/bridge/server.ts calls `httpServer.listen(this.port, ...)` with no host, which in Node binds every network interface, not only loopback. The WebSocket upgrade accepts any client with no token and no Origin check, and a new connection replaces the current bridge client. The optional HTTP transport (threejs-devtools-mcp-http, port 9223) is an unauthenticated MCP endpoint with `Access-Control-Allow-Origin: *`, also on every interface.
- Security notes: Verified exposure in v0.5.0. (1) Anyone on the same Wi-Fi or LAN can open http://<the PC's address>:9222 and reach the dev site through the proxy, even when the dev server itself listens only on localhost. macOS has its firewall off by default; Windows shows a firewall prompt that is easy to accept. (2) The same person, or a web page open in the owner's browser, can connect a WebSocket to port 9222 and take over as the page: it then receives the agent's commands, including run_js code, and can send forged tool results back into Claude's context, which is a prompt-injection channel into a session that can edit files and run commands. (3) With the HTTP transport, anyone on the network can call all 69 tools, including set_dev_port, which turns the proxy into a route to other localhost services. (4) It opens a browser tab and the listener on every Claude Code start while configured; open issue #7 asks for lazy start-up. (5) The npm package has one maintainer account, no provenance attestation and ships only a bundled dist that I did not audit, so the source review does not prove the published tarball; npm metadata shows no install scripts. No advisories found; a scanner listing rated a wrapper skill medium risk for running an unverifiable npx package. It would move to usable if it bound to 127.0.0.1, checked Origin or a token and started lazily; until then use only with inbound 9222 and 9223 blocked, stdio transport, a pinned version, project scope and removal after the look-dev phase.
- Maturity: v0.5.0 on 2026-10-14; 41 commits, 37 by one developer; tags 0.1.1 to v0.5.0; CI only type-checks and builds, the tests folder is not run in CI; 2 issues (1 open); a package scanner reported about 130 weekly downloads for an early version. A small single-developer project.
- Corrections found during verification: "Opens a browser on a debugging port (localhost:9222)" is wrong: 9222 is the server's own proxy and WebSocket bridge port; Chrome's debugging protocol is exposed only when CDP_PORT is set. "No release tags visible" is wrong: there are 6 tags. "Node and Chrome versions not stated" is wrong for Node: 22.18 or newer. "Telemetry not documented": none exists in the source. The advice "use on localhost only" cannot be followed by configuration, because the server binds all interfaces and has no host option. 69 tools, MIT, stars and push date are confirmed. The npm latest version is 0.5.0 and matches the repo's package.json.

## State of the field, by angle

### blender-control

No single skill does the whole job the owner imagines. Nothing found builds a realistic human, dresses it in a draped T-shirt with front and back prints, bakes textures and ships a phone-ready GLB into a three.js page; it has to be assembled from parts, and the human and garment steps will need a project-specific skill written for this pipeline.

What exists now (November 2026):
- An official bridge. Blender Lab's MCP server launched with Anthropic's Blender connector on 2026-04-28 (Anthropic also became a Blender Development Fund patron). It is minimal: scene summaries, viewport screenshots, docs lookup, execute_blender_code. It needs Blender 5.1+ and is hosted on projects.blender.org, not GitHub. I found no Anthropic-authored Blender skill or plugin.
- The community bridge ahujasid/mcp-for-blender (35.9k stars, renamed from blender-mcp) remains the most used and adds asset libraries and 3D generators, with a weaker safety record (four CVEs in 2026, unauthenticated socket, default anonymous telemetry).
- Safety-first bridges are appearing: blenderwright (signed socket, raw Python off), mohakmalviya/frugal-blender-mcp (4 tools, token, permission-gated Python, 18 stars) and Scenario's Blender plugin (execute_python off by default).
- A wave of skill packs and plugins: EL4CTEO/blender-skills, scenario-labs/skills, blender-kiln, blender-agent-studio, majidmanzarpour/blender-game-skills, RobLe3/cc-blender-skill (30 MCP-only skills, MIT, 187 stars), arjun988/blender-skills. Nearly all target game assets, props, product shots or 3D printing.

What is strong: connecting Claude to Blender, Blender 5.x API conventions, headless runs, high-to-low baking, GLB export with re-import checks, and screenshot-based self-review loops. The no-bridge route (Claude writes bpy scripts and runs `blender -b --factory-startup -P script.py`) is well supported by skills and is the lowest-exposure option; a live bridge mainly adds the ability to watch and inspect the viewport.

What is missing or weak:
- Humans: no mature skill wraps a human generator. MPFB2 (makehumancommunity/mpfb2, 736 stars, GPL code with CC0 base mesh) is drivable headless, but the only MPFB skills found are small and project-specific (one in conorluddy/vcr validated only for a default human; one MakeClothes garment skill inside simnova/OpenClinXR).
- Garments: only EL4CTEO's blender-clothing gives concrete scripts, and it is game-oriented. No skill covers print placement or apparel-grade drape.
- Sculpting: brush strokes are not available to agents (not exposed by blenderwright, failing or crashing headless per Scenario), so "sculpting" means cloth simulation, modifiers and baked normal maps.
- Blender-to-three.js handoff: covered only by small skills (vladmdgolam/agent-skills) and kiln.

Safety: every bridge runs arbitrary Python as the logged-in user; Blender's own announcement says the official server has no guards. Sensible posture for a personal PC: one bridge at a time (the official and community add-ons share port 9876), work on copies, keep Claude Code's permission prompts on for Blender commands, prefer headless for bake and export, pin versions, and install only from the exact repositories named. GitHub search today surfaced a cluster of look-alike "blender-ai-copilot" repositories that fit a known malware distribution pattern.

Limits of this research: blender.org, strayspark.studio and dev.classmethod.jp were unreachable (they would have to be allowed in the session's network settings), so facts about the official server come from search snippets and third-party READMEs. Nothing was cloned or run; star counts are as returned by GitHub search and not verified as organic.

### human-and-cloth-in-blender

No single skill does the whole job the owner imagines (body, sewn and draped heavy-cotton T-shirt with prints, bake, web-ready GLB). Nothing found wraps a human generator together with garment sewing, and a code search for skills mentioning MPFB returned only narrow, project-specific recipes. The job has to be assembled, ideally as one small project skill that calls Blender headless.

What is strong:
- Body: MPFB 2 is the clear choice. Its output is explicitly unrestricted, it has script samples, and it ships rigs (default, mixamo, game_engine, Rigify), so no separate auto-rigger is needed.
- Skill layer: EL4CTEO/blender-skills is the nearest ready-made pack (clothing, baking, retopology, QA, web GLB preset, headless). It needs Blender 5.2 LTS or newer and is aimed at fitted game clothing, not an oversized draped tee.
- Web step: the bundled glTF exporter plus glTF-Transform or gltfpack is mature and scriptable.

What is missing or weak:
- No free, current, GitHub-hosted pattern-and-sew garment add-on. Seams to Sewing Pattern is on GitLab and dates from Blender 2.8-3.0. Current pattern tools are paid: Simply Cloth Studio 2.0 (about USD 170 commercial), Garment Studio beta (about USD 60; Windows, NVIDIA, Blender 5.2+), Garment Tool, and Easy Cloth (price not confirmed).
- The realistic route is a scripted T-shirt (four to six panels, or GarmentCode's t-shirt preset) sewn with Blender's classic Cloth modifier: sewing springs on loose edges, `use_sewing_springs`, a bounded `sewing_force_max`, shrink eased in, self-collision, body as collider.
- No source in this session gave confirmed heavy-cotton values; the starting point is Blender's built-in Cotton and Denim presets, tuned by eye.
- Blender 5.2 LTS (July 2026) added an experimental Geometry Nodes XPBD "Cloth Dynamics" system, but its manual says self-collision is missing, so it is not yet the tool for garments.
- ppf-contact-solver is the high-quality open alternative, with its own Blender add-on and MCP server, but it is self-described as not production ready and wants an NVIDIA GPU.
- Prints need no decal add-on: place the small front and large back artwork in the base-colour texture on the shirt's UV layout. Fold detail goes into a baked normal and AO map from the dense drape onto a decimated or remeshed copy. Real-time cloth on a phone is not realistic; ship the baked drape.

Licence traps seen:
- The GarmentCode simulator fork is non-commercial (NVSCL).
- SMPL / SMPL-X topologies are non-commercial (Anny warns it may download them).
- CharMorph inherits MB-Lab base meshes with unclear terms.
- Some MakeHuman asset packs are CC-BY (credit required).

Safety notes for a personal PC:
- Search results contained keyword-stuffed repos from random-named accounts with about 500 stars each (several "blender-ai-copilot-*", an "ai-texture-forge") and a non-official "makehuman for Windows" repo. Treat these as untrusted and install nothing from them.
- Many repos mirror the two skill packs; use upstream only.
- Security press from late 2025 to February 2026 reported info-stealer malware in free .blend files that runs when "Auto Run Python Scripts" is on. Keep that setting off and take MPFB only from the official extensions platform or the makehumancommunity org.
